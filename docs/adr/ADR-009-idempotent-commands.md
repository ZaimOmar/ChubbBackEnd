# ADR-009: Idempotent commands in Claims (Idempotency-Key)

Status: Accepted. The four open points (role-policy 403s, in-flight duplicates, scope incl. corrections and settlement stubs, Officer release on reassign) are **DECIDED (human, 2026-10-28)** as recommended (marked below). Owner: architect. Rules: BR-79 to BR-87. Related: ADR-004 (reliability), ADR-005 (maker-checker, refused entries; amended by this ADR).

## Context
Claimants on mobile networks and officers who double-click resend commands. Without a key a resend can create a second claim, a second "Information received" entry or a second Refused entry, which corrupts the trail (BR-04) and the metrics built on it. Human decisions: a key is mandatory on **every create-style command**, retention is 24 h, .NET 8 stays. The record must commit atomically with state, trail and outbox (BR-84), and an in-flight duplicate must never execute twice or write a Refused entry (BR-85).

## Decision
I agree with the BA's approach (BR-79 to BR-87). The concrete mechanics:

**Store.** Table `idempotency_keys` in `claims_db`: `actor_id uuid`, `route text` (method + route template with ids substituted in canonical form, e.g. `POST /claims/3f2c.../decision-proposals/9ab1.../confirm`, GUIDs lower-case `D` format), `idempotency_key varchar(128)`, `request_hash bytea` (SHA-256 of method, canonical route and raw body bytes), `status_code int`, `response_body bytea`, `content_type text`, `location text null`, `created_at`, `expires_at` (= created_at + `Idempotency:Retention`, default 24 h). Primary key `(actor_id, route, idempotency_key)`; index on `expires_at`; `CHECK (status_code BETWEEN 200 AND 499)`. No FK to `claims` (`POST /claims` has no claim yet). **No pending/completed status column:** the row is only ever visible after its transaction commits, so every visible row is complete and a crash can never leave a stuck "pending" key.

**Claiming the key: transaction-scoped advisory lock, row written at the end.** One transaction per command, owned by the filter:
1. Authentication and the role policy run first (middleware). A missing or malformed key returns 400 before any transaction (BR-79).
2. `BEGIN`; `SELECT pg_try_advisory_xact_lock(hashtextextended(actor_id || route || key, 0))`. `false` means the same scope is in flight: rollback and return 409 `idempotency-request-in-progress`, `Retry-After: 1`. The handler never runs, so no Refused entry (BR-85).
3. `SELECT` the row for the scope. Unexpired, same hash: return the stored status, body, `Content-Type`, `Location` with `Idempotent-Replayed: true` (BR-82). Unexpired, different hash: 422 `idempotency-key-reused`, stored body not revealed (BR-83). Expired: `DELETE` it in this transaction and continue as new (BR-87).
4. `SAVEPOINT command`; run validation and the handler. Handlers call `SaveChangesAsync` but never begin or commit.
5. Decide storability (BR-86): 2xx, or a 4xx where a Refused entry was written (step 6), is stored: insert the row, `COMMIT`. Anything else (400 validation, trail-less 422, 404) is `ROLLBACK`, nothing kept, and the client may reuse the key. Exceptions (5xx) roll back the whole transaction, so no record survives (BR-84).
6. **Refused entries inside the same transaction.** A domain refusal (`DomainRefusalException` with claimId, problem type, status, summary) is caught by the filter: `ROLLBACK TO SAVEPOINT command`, clear the EF change tracker, insert the Internal Refused entry through `IRefusedAttemptRecorder`, then store the refusal response with the key row and commit. This replaces ADR-005's "own small transaction": the effect is the same (domain changes discarded, the entry persists) and the entry and the stored refusal are atomic, so a replay returns the same refusal and never writes a second entry.

The primary key is the backstop: if a unique violation still occurs on insert, the filter rolls back and returns 409 `idempotency-request-in-progress`.

**Interaction with concurrency.** The advisory lock is always taken before any row lock, so lock order is fixed and no deadlock is introduced. Same key: serialised by the advisory lock, the claim is never touched by the duplicate. Different keys (two managers, two officers): not serialised; they meet at the claim's optimistic token (`xmin` mapped as `rowVersion`). The loser gets `DbUpdateConcurrencyException`, which is a domain refusal (409 `concurrency-conflict` or `claim-already-assigned`) plus a Refused entry (BR-26, BR-38), stored under the loser's own key. Pick-up uses the row version, not `FOR UPDATE SKIP LOCKED`; `SKIP LOCKED` is kept for the outbox publisher, where skipping is the point. Do not enable `EnableRetryOnFailure` on the Claims DbContext: a retrying execution strategy conflicts with a filter-owned transaction and would re-run handlers.

**Where the code lives.** `src/Claims/Api/Idempotency/`: `IdempotencyFilter` (`IEndpointFilter`, registered with `.WithIdempotency()` on every command), `RequestBufferingMiddleware` (calls `EnableBuffering()` only for endpoints with idempotency metadata, so the raw bytes can be hashed after model binding; the Claims Kestrel body limit is 64 KB), and a key-format validator. `src/Claims/Application/`: `IIdempotencyStore`, `IRefusedAttemptRecorder`, `DomainRefusalException`. `src/Claims/Infrastructure/Idempotency/PostgresIdempotencyStore` (lock, lookup, delete-expired, insert) and the recorder implementation. The filter turns the handler's typed result (`IStatusCodeHttpResult`, `IValueHttpResult`, `Created<T>.Location`, `ProblemHttpResult`) into bytes with the application's JSON options and returns those exact bytes, so the first response and every replay are byte-identical. Header names go in `Contracts.HeaderNames` (`IdempotentReplayed`).

**Amended 2026-10-28 (architect, claims-persistence review): executor and filter split.** Steps 2 to 6 live in an HTTP-free `IdempotentCommandExecutor` in `src/Claims/Application/Idempotency/`. It takes the scope, the request hash and two delegates: run the handler, and turn a result or refusal into a `StoredResponse` (status, body bytes, content type, location). `IdempotencyFilter` in Api becomes a thin adapter. It validates the key format (a missing or empty header gives `idempotency-key-missing`; several values or a bad format give `idempotency-key-invalid`), takes the actor from the token, builds the canonical route, reads the buffered raw body, calls the executor and writes the bytes it gets back. Why: the atomicity, replay, reuse, in-flight, expiry, 5xx and stored-refusal behaviour (I1 to I3, I5 to I8, S33) can then be tested with Testcontainers without HTTP and without test-only endpoints that would copy the middleware order. The HTTP-pipeline cases (I4 key format, S12 role policy before the key, S34 logs, S35 401 before lookup) are tested through the real routes. Alternatives rejected: test-only endpoints in the test project (they rebuild the pipeline order the tests are meant to check, and are thrown away later); moving every idempotency test to the endpoints spec (the core logic would stay untested until the last Claims spec). Ownership: the executor, store and recorder are spec 2; the filter adapter, buffering middleware and `ProblemResults` are spec 3.

**DECIDED (human, 2026-10-28) (1): role-policy 403 vs BR-04.** BR-04 trails "every refused attempt by an authenticated user, including unauthorised action"; BR-86 stores only responses that wrote a trail entry. Decision (as recommended): a 403 from the **role policy** (e.g. an Officer-only user calling confirm, a Claimant calling assign) is logged as a structured security event (actor, route, claimId, correlationId) but **not** trailed and **not** stored. A claimant failing the **ownership** rule gets 404 `claim-not-found`, also logged, not trailed. "Unauthorised action" in BR-04 then means a resource-rule refusal after the role policy passed: non-assigned officer, maker equals checker (also for a dual-role user), non-maker withdraw, Correction by a non-assigned officer. These are trailed and stored. Why: the role policy runs in ASP.NET authorisation middleware before the handler; to trail it we would need a custom `IAuthorizationMiddlewareResultHandler` that looks up the claim and writes to its trail. That would let any authenticated user (a claimant probing ids, say) write entries into other people's claim trails (trail flooding), would reveal claim existence through the different write paths, and would move key handling ahead of authorisation. Consequence: the BA amends the BR-04 wording; S3 and S12 assert 403, **trail entry count unchanged**, no idempotency record, one security log event; S11 and I8 (dual-role maker) still assert one Refused entry and a stored, replayable 403. Alternative rejected: BR-04 read literally (trail role-policy 403s for staff callers on an existing claim via that handler); it costs about 45 minutes and adds the risks above.

**DECIDED (human, 2026-10-28) (2): in-flight duplicate = 409, not wait-then-replay.** Decision (as recommended): 409 `idempotency-request-in-progress` with `Retry-After: 1` (as BR-85 and US-06 state). It is deterministic in tests, holds no connection while waiting, and the client already has to retry on network errors. Wait-then-replay is a small switch: replace `pg_try_advisory_xact_lock` with `pg_advisory_xact_lock` under `SET LOCAL lock_timeout = '5s'`, and step 3 then finds the committed row and replays it. The cost is a pooled connection and a request thread held per waiting duplicate; it stays a documented alternative, not built. Test I3 asserts the 409 with `Retry-After: 1` (and the replay after retry).

**Agreed with the BA, recorded here:** the raw-body fingerprint has no JSON canonicalisation (BR-81). The frontend must keep the serialised body bytes with the key and resend those exact bytes, not re-serialise.

**DECIDED (human, 2026-10-28) (3): scope.** The BA's ten commands plus `POST /claims/{id}/corrections` and the Phase 1 settlement stubs (which answer 409 `phase-2-not-enabled`, Refused, stored), because the human decision says "all create-style commands". A startup test fails if any non-GET Claims endpoint lacks idempotency metadata.

**DECIDED (human, 2026-10-28) (4): Officer release on reassign.** `POST /claims/{id}/reassign` is the one route for both: a Manager may reassign any open, non-Submitted claim; an Officer may call it only as the current assignee, and "release" means handing the claim to a named officer (`newOfficerId` required), never back to Submitted or the pick-up queue (BR-76). A non-assignee officer gets 403 `not-assigned-officer` (resource rule, so Refused and stored).

## Alternatives considered
- **Insert a pending row in its own committed transaction first, then complete it:** gives "in progress" visibility, but a crash leaves a stuck pending key that needs a lease and a sweeper, and it breaks BR-84 (a record would survive a failed command). Rejected.
- **Insert the row only at commit and rely on the unique violation (no lock):** both duplicates run the handler. The second then usually fails on the claim's row version, not on the key, so it writes a Refused entry, which BR-85 forbids, and it burns a claim number on `POST /claims`. Rejected; the unique key stays only as a backstop.
- **`INSERT ... ON CONFLICT` placeholder at the start of the same transaction:** correct, but the duplicate blocks on the uncommitted row (that is wait-then-replay, without a timeout knob). The advisory lock gives the same serialisation with an explicit choice between try and wait. Rejected in favour of the lock.
- **Redis or in-memory cache:** not atomic with the Postgres transaction, and adds a component. Rejected.
- **Gateway-level idempotency:** the Gateway has no database and cannot be atomic with the command. Rejected.
- **Natural idempotency only (state machine refuses duplicates):** a duplicate `POST /claims` creates a second claim, and every duplicate refusal adds a Refused entry. Rejected (this is the BA's problem statement).

## Consequences
- Every Claims command runs in one filter-owned transaction (advisory lock, savepoint, commit). Integration tests I1 to I8 plus S32 to S35 (SECURITY-REQUIREMENTS) need Testcontainers Postgres; advisory locks cannot be tested on SQLite or in-memory.
- Stored bodies can hold personal data (answer text, claim details). They are readable only by replay to the same actor, never logged (no body logging, EF `EnableSensitiveDataLogging` off), and deleted or ignored after 24 h. Encryption at rest is a production gap.
- After expiry, a resent `POST /claims` creates a second claim; the officer rejects it with `DUPLICATE_CLAIM` (BR-87).
- Gateway CORS must also expose `Retry-After` and `Location` (it already allows `Idempotency-Key` and exposes `Idempotent-Replayed`). The OpenAPI contract declares the header and the four problem types on each command.
- ADR-005's "own small transaction" for refused entries is superseded by the savepoint approach above; ARCHITECTURE section 3a is updated.
- About 60 to 90 minutes in slice 1a (filter, store, tests); worth it because it protects the trail, which is the assessed centrepiece.
